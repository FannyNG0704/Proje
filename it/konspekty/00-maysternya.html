1. Файли, папки і шляхи

Будь-яка програма — це просто текстові файли, які лежать у папках на диску. Код у VS Code і код у Блокноті — це той самий файл; редактор лише зручніше його показує.

Шлях — це «адреса» файлу: перелік папок від диска до файлу. Наприклад, C:\Users\gladu\kursy\README.md читається так: диск C → папка Users → папка gladu → папка kursy → файл README.md.

C:\Users\gladu — твоя домашня папка. Тут належить тримати свої проєкти: у корені диска (C:\) бувають проблеми з правами, і туди гірше доходять резервні копії.

Два спеціальні позначення: . (одна крапка) — «папка, де я зараз»; .. (дві крапки) — «папка на рівень вище». Тому cd .. — «піднятись вгору», а code . — «відкрий у VS Code поточну папку».

АналогіяШлях — як поштова адреса: країна → місто → вулиця → будинок. .. — «вийти на попередню вулицю», . — «тут, де стою».

2. Термінал

Термінал — вікно, де ти керуєш комп'ютером текстом замість мишки. Пишеш команду, натискаєш Enter — комп'ютер виконує. Навіщо, якщо є мишка? Бо сервери, на яких живуть сайти, мишки не мають взагалі, а багато інструментів (Git, Node) працюють саме через команди.

У тебе термінал — PowerShell (на Windows). На Mac і серверах — інші (zsh, bash), але ідея та сама.

Як читати рядок терміналу

PS C:\Users\gladu\kursy> _

PS — це PowerShell; C:\Users\gladu\kursy — папка, в якій ти зараз «стоїш»; > — «готовий, пиши команду».

Команди, які ти вже знаєш

Різниця, яку питали: mkdir створює папку, але ти лишаєшся там, де був. cd нічого не створює — він переносить тебе в існуючу папку. Спочатку побудував кімнату (mkdir), потім зайшов у неї (cd).

Як читати відповідь терміналу

Червоний текст — помилка. Тиша після Enter — успіх (багато команд нічого не пишуть, якщо все добре). Порожній результат ls — просто порожня папка. «is not recognized» майже завжди означає одруківку в назві команди або програму, якої не встановлено.

Камені, на які ти вже наступав Enter натискається один раз, у кінці команди — інакше термінал виконає половину. Текст, який не є командою (node_modules/), в терміналі не має сенсу — йому місце у файлі. Стрілка ↑ повертає попередню команду, Tab дописує назви, Esc стирає рядок.

3. VS Code: з чого складається вікно

VS Code — редактор коду. Він не «запускає» програми сам по собі: він показує файли, допомагає їх писати і має всередині термінал.

Ліва панельExplorer (файли) або Source Control (Git)Бачиш файли проєкту або зміни для коміту
ПосерединіРедакторПишеш вміст файлів

Open Folder — найважливіша дія: VS Code має знати, яка папка — твій проєкт. Без неї ліворуч «No Folder Opened», і Git та інші інструменти не розуміють, з чим працювати.

Довіра до папки (Trust): VS Code питає, чи довіряєш авторам файлів, бо проєкт може містити код, який запуститься сам. Своїм папкам — довіряй, чужим завантаженим — спершу подивись, що там.

Крапка ● на вкладці файлу — є незбережені зміни. Ctrl+S зберігає мовчки, і крапка зникає. «M» біля файлу — Modified: змінено відносно останнього коміту.

КаміньCopilot у режимі агента питає «Run command? Allow / Skip». Завжди читай команду перед Allow і ніколи не вмикай «Always allow». І не запускай AI у файлах із справжніми паролями й ключами — вміст іде на сервер AI.

4. Node.js

JavaScript від народження живе в браузері. Node.js — «двигун», який дозволяє запускати JavaScript просто на комп'ютері чи сервері: ботів, сервери, скрипти. Поки ти його лише встановив; знадобиться з P2–P5.

LTS (Long Term Support) — версія, яку довго підтримують і виправляють. Для навчання і роботи завжди LTS, а не «Current» (найновіша, але менш стабільна).

npm — менеджер пакетів, що приходить разом з Node: через нього підключаєш чужі бібліотеки. Вони складаються в папку node_modules.

5. Git і GitHub — у чому різниця

Git — програма на твоєму комп'ютері. Вона пам'ятає історію змін у проєкті: що, коли і навіщо змінено. Працює без інтернету.

GitHub — сайт, куди Git відправляє копію твого проєкту. Там зручно зберігати, показувати і працювати разом з іншими.

АналогіяGit — як фотоапарат, що знімає твій проєкт після кожної зміни. GitHub — як хмарний фотоальбом, куди ти завантажуєш знімки, щоб вони не загубились і їх могли бачити інші.

Тому вхід у GitHub через VS Code ≠ встановлений Git: перше — доступ до альбому, друге — сам фотоапарат.

git config --global user.name / user.email — ти «підписуєш» фотоапарат: кожен знімок (коміт) матиме твоє ім'я і пошту. --global — для всіх проєктів на цьому комп'ютері.

6. Репозиторій і коміт

Репозиторій («репо») — папка проєкту, за якою стежить Git. Звичайну папку перетворює на репозиторій команда git init: вона створює приховану папку .git, де живе вся історія. Видалиш .git — зникне історія, файли залишаться.

Коміт — «знімок» стану файлів у певний момент, з твоїм підписом-поясненням. У кожного коміту є ID — довгий код, з якого зазвичай показують перші 7 символів: b3fe5e2, 677ea93…

Історію подивитися: git log --oneline. Найновіший коміт — зверху. Перший коміт в історії Git позначає як root-commit.

1 file changed, 2 insertions(+), 1 deletion(-) — скільки файлів і рядків змінилось. Git не вміє «редагувати» рядок: для нього зміна = видалив старий + вставив новий.

7. Три «місця» в Git

Найважливіша схема всієї майстерні. Зміна проходить три етапи:

flowchart LR
  W["Робоча папка
файли, які ти редагуєш"] -->|git add| S["Staging
«що піде в знімок»"]
  S -->|git commit| L["Локальна історія
коміти на твоєму ПК"]
  L -->|git push| R["GitHub
копія в хмарі"]
  R -->|git pull| L

Робоча папка — файли, як вони зараз на диску. Staging («сцена») — те, що ти вибрав для наступного знімка. Навіщо проміжний етап? Щоб у один коміт потрапили тільки пов'язані зміни, а не все підряд. Локальна історія — збережені коміти, поки тільки в тебе.

git commit -am "..." — скорочення: add + commit одразу, але тільки для файлів, які Git уже знає (новий файл через -am не потрапить).

git status — головна команда-«ліхтарик»: показує, в якій ти гілці, що змінено, що в staging, що не відстежується. Запускай її завжди, коли не впевнений. «nothing to commit, working tree clean» — змін немає (найчастіше: забув зберегти файл).

Різниця commit і push: commit — зберегти знімок у себе. push — відправити збережені знімки на GitHub. Можна зробити 10 комітів без інтернету, а потім один push.

8. Гілки і main

Гілка — окрема лінія історії, в якій можна працювати, не чіпаючи основну. main — назва головної гілки: там лежить «чиста», робоча версія проєкту. Решта гілок — для окремих задач: fix-readme, variant-a…

gitGraph
  commit id: "README"
  commit id: "опис P0"
  commit id: "список команд"
  branch fix-readme
  commit id: "абзаци"
  checkout main
  merge fix-readme

git switch -c назва — створити гілку і перейти в неї. git switch main — повернутись у main. git branch -d назва — видалити гілку (історія, вже злита в main, лишається).

HEAD — «ти тут»: на якій гілці і коміті ти зараз. HEAD -> main означає «я на гілці main».

Навіщо гілки, якщо можна все в main? Main має завжди працювати. Якщо експеримент не вдався — гілку просто видаляєш, main не постраждав. У команді кожен працює у своїй гілці, і люди не заважають одне одному. А зміни потрапляють у main тільки після перевірки (pull request).

Аналогіяmain — чистовик зошита. Гілка — чернетка, де пробуєш рішення. Вийшло — переписуєш у чистовик (merge). Не вийшло — викидаєш чернетку.
КаміньПеред роботою дивись, у якій ти гілці (внизу ліворуч у VS Code або git status). Найчастіша помилка — працювати в main, думаючи, що ти у своїй гілці.

9. GitHub: push, pull, clone

КомандаНапрямокКоли
git pushТвій ПК → GitHubВідправити свої коміти
git pullGitHub → твій ПКЗабрати нове в вже існуючий у тебе проєкт
git clone адресаGitHub → твій ПКПерший раз завантажити проєкт, якого в тебе ще немає
git fetchGitHub → твій ПКЛише дізнатись, що нового, нічого не змінюючи у файлах

Різниця pull і clone: clone — «скопіювати весь проєкт з нуля» (робиться один раз). Pull — «докачати оновлення» в проєкт, який уже є.

origin — коротке ім'я твого репозиторію на GitHub (щоб не писати повну адресу). origin/main — гілка main на GitHub, як її пам'ятає твій комп'ютер.

git push -u origin fix-readme — перший push нової гілки: -u «зв'язує» її з GitHub, і далі достатньо просто git push.

«Your branch is up to date» — актуально на момент останнього pull/fetch, а не «зараз». Тому ти бачив «up to date», хоча на GitHub уже був злитий PR, — комп'ютер ще про нього не знав.

«ahead of origin/main by 1 commit» — у тебе є 1 коміт, якого ще немає на GitHub. Треба push.

Private / Public: приватний репозиторій бачиш тільки ти (і кого запросиш), публічний — увесь інтернет.

10. Pull request і злиття

Pull request (PR) — запит «будь ласка, злийте мою гілку в main». На GitHub це сторінка, де видно всі зміни (вкладка Files changed), можна обговорити і перевірити їх, а потім натиснути Merge. У командах саме тут колега робить рев'ю твого коду.

Merge (злиття) — перенести зміни з однієї гілки в іншу. Буває двох видів:

Fast-forward — якщо в main нічого нового не з'явилось, Git просто «пересуває» main вперед до останнього коміту гілки. Нового коміту не створює.

Merge commit — якщо обидві гілки мають свої нові коміти, Git створює окремий «коміт злиття», що об'єднує дві лінії (на графіку дві лінії сходяться в одну точку).

Після злиття на GitHub твій комп'ютер про це не знає — тому git switch main → git pull.

11. Конфлікт

Конфлікт — коли дві гілки змінили один і той самий рядок по-різному. Git не вгадує, яка версія правильна, і просить вирішити людину. Якщо змінено різні рядки чи різні файли — Git зливає сам.

<<<<<<< HEAD (Current Change)
# Мої IT-курси            ← що вже є там, де ти зараз
=======
# Моє навчання            ← що приходить з іншої гілки
>>>>>>> variant-b (Incoming Change)

Current — «поточне», версія в гілці, куди зливаєш (у тебе main). Incoming — «вхідне», версія з гілки, яку зливаєш. Вирішення: залишити одну, обидві або написати свою — і обов'язково прибрати всі позначки <<<, ===, >>>. Потім git add + git commit.

КаміньGit дозволить закомітити файл разом з позначками конфлікту, ніби це звичайний текст. У коді програми це миттєва помилка. Перед add — переконайся, що позначок не лишилось.

12. .gitignore і секрети

.gitignore — файл зі списком того, що Git має ігнорувати: ніколи не додавати в коміти і не відправляти на GitHub. Назва починається з крапки — так у світі програмування позначають службові файли.

Чому node_modules/: там тисячі чужих файлів бібліотек, які займають сотні мегабайт і завжди відновлюються однією командою npm install. Зберігати їх у Git — як фотографувати весь магазин замість списку покупок.

Чому .env: туди кладуть секрети — паролі, API-ключі, токени. Якщо вони потраплять на GitHub, їх можуть знайти боти за хвилини і скористатись.

Що робити першим, якщо ключ уже потрапив на GitHub: негайно замінити (відкликати) сам ключ у сервісі, якому він належить, — створити новий, а старий вимкнути. Видалити файл з репозиторію недостатньо: ключ лишається в історії комітів, і його могли вже скопіювати. Спершу — новий ключ, потім — прибирання.

Камінь.gitignore не допомагає, якщо файл уже був закомічений — Git і далі за ним стежить. Тому .gitignore створюють на самому початку проєкту, до першого секрету.

13. README і Markdown

README.md — «обкладинка» проєкту: що це, як запустити. GitHub показує його на головній сторінці репозиторію.

Markdown (.md) — простий спосіб оформити текст символами: # — великий заголовок, ## — менший, 1. — нумерований список, `код` — код.

Правило, на якому ти спіткнувся: звичайний перенос рядка в Markdown не створює новий абзац — рядки зливаються. Новий абзац — тільки після порожнього рядка.

15. Весь шлях одною картинкою

Ось що ти зробив за один вечір — повний цикл роботи, яким щодня користуються програмісти в усьому світі:

flowchart TD
  A[Встановив VS Code, Node.js, Git] --> B[Навчився ходити по папках у терміналі]
  B --> C[git config: підписав свої коміти]
  C --> D[git init: папка стала репозиторієм]
  D --> E[Редагував файл → add → commit]
  E --> F[Publish: репозиторій на GitHub]
  F --> G[Гілка → коміт → push]
  G --> H[Pull request → Merge → pull]
  H --> I[Конфлікт → вирішив → commit]
  I --> J[.gitignore: секрети не потрапляють на GitHub]

Цей цикл — гілка → зміни → коміт → push → PR → merge → pull — не зміниться, хоч ти робитимеш сайт, гру чи AI-продукт. Усе інше в курсі будуватиметься поверх нього.

Далі — P1: сайт-візитка. Тепер ти вмієш зберігати свою роботу і відправляти її на GitHub; наступний крок — нарешті зробити щось, що можна побачити в браузері.
